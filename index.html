func (r *MyAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app myappv1.MyApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    // 读 spec，创建/更新 Deployment 等子资源
    dep := deploymentFor(&app)
    if err := controllerutil.SetControllerReference(&app, dep, r.Scheme); err != nil {
        return ctrl.Result{}, err
    }
    // CreateOrUpdate ...
    app.Status.ReadyReplicas = ...
    return ctrl.Result{RequeueAfter: time.Minute}, r.Status().Update(ctx, &app)
}

02 / Informer Internals

Informer：从 List-Watch 到 Reconcile 的事件管道

Informer 不是 Watch 的别名。它在 List-Watch 之上增加自动重连、本地缓存、索引、事件分发与共享机制，是 Kubernetes Controller 的核心读模型。

DATA PATH① 同步本地缓存目标是让 Indexer 尽量接近 apiserver 中的最新状态。
SOURCEkube-apiserverList 给出全量快照和 resourceVersion；Watch 从该版本继续给增量。
CONNECTReflector通过 ListWatcher 执行 ListAndWatch，并处理断线重连与重新 List。
BUFFERDeltaFIFO按对象 key 暂存 Added、Updated、Deleted、Replaced、Sync 等 Delta。
APPLYHandleDeltas逐个消费 Delta：先更新 Indexer，再发出相应的 Add/Update/Delete 通知。
CACHEIndexer / Lister保存对象最新快照和索引；Lister 与缓存型 client 从这里读取。
SIGNAL PATH② 触发业务重算目标不是保存每条事件，而是提醒某个 key 需要再次对齐。
FAN-OUTSharedProcessor把缓存变更通知分发给多个 ResourceEventHandler。
MAPEventHandler过滤事件并映射为 key；通常是 namespace/name，不在这里做耗时业务。
SCHEDULEWorkQueue对 key 去重；失败时限速退避，处理期间再变化则安排再处理一次。
CONSUMEWorker从队列取 key，调用 syncHandler 或 Reconcile；完成后 Done / Forget。
CONVERGEReconciler拿 key 从 Cache 重新读取最新对象，比较期望与现状并写回 API。
先抓住边界：上面一条是数据通路，把 apiserver 的对象同步成可查询的本地快照；下面一条是信号通路，只把“哪个 key 可能需要重算”交给 Controller。事件是闹钟，不是业务事实；Reconcile 的事实来源是它执行时重新读到的最新对象。

DeltaFIFO：服务于缓存同步

内容：同一对象 key 对应的一组 Delta，例如 Added / Updated / Deleted。

消费者：SharedIndexInformer 的处理循环。它消费 Delta、更新 Indexer，并触发 Handler 通知。

不是：它不是 Reconcile 的任务队列，也不负责业务失败重试。

WorkQueue：服务于业务调度

内容：通常只有 namespace/name key，不保存事件快照或完整对象。

消费者：Controller worker。worker 取 key 后，再从 Cache 读取对象当前版本。

价值：合并同一 key 的事件风暴，并为失败提供限速退避。

一次 MyApp/default/demo 更新到底发生什么

1 · 持久化用户 PATCH MyApp；apiserver 写入 etcd，resourceVersion 从 41 变成 42。
2 · WatchReflector 收到 MODIFIED，转换成 Updated Delta 放入 DeltaFIFO。
3 · 更新缓存HandleDeltas 把 rv=42 的对象写入 Indexer。
4 · 发通知SharedProcessor 调用已注册 Handler 的 UpdateFunc。
5 · key 入队Handler 只生成 default/demo；WorkQueue 对重复 key 去重。
6 · 重新读取worker 取出 key；Reconcile 从 Cache Get，可能已读到比 42 更新的版本。
7 · 状态收敛按当前 spec 创建或更新子资源、回写 status；失败则限速重试。
为什么队列里只放 key？假设 rv=42、43、44 在 worker 执行前连续到达，逐条保存旧对象没有意义。队列只需保留“default/demo 要处理”，Reconcile 一次读取 rv=44，直接向最新期望状态收敛。

每个内部组件到底做什么

ListWatcher

定义如何访问某类资源。第一次 List 建立全量基线，随后 Watch 从返回的 resourceVersion 继续消费增量。

Reflector

长期运行 ListAndWatch。Watch 正常断开会重连；版本过旧出现 410 Gone 时重新 List，而不是让业务控制器处理连接恢复。

DeltaFIFO

位于 Reflector 与 Informer 处理循环之间，按对象 key 聚合一组 Deltas。它不是 Reconcile 使用的业务 WorkQueue。

Indexer

线程安全地保存每个 key 的最新对象。Lister 只读这个本地缓存；索引让控制器可按 namespace、owner 等条件快速查找。

Processor

SharedInformer 的 fan-out 层。一个底层 List-Watch 和 Store 可以服务多个 Handler，避免每个 Controller 都向 apiserver 建连接。

Handler

AddFunc/UpdateFunc/DeleteFunc 不应执行耗时业务，只负责过滤事件、生成 key 并加入 WorkQueue。

WorkQueue

用 dirty/processing 集合合并同一 key 的事件。处理期间再次变化会在 Done 后重新入队，保证最终还能再对齐一次。

client-go 典型骨架

factory := informers.NewSharedInformerFactory(client, 30*time.Minute)
podInformer := factory.Core().V1().Pods()

podInformer.Informer().AddEventHandler(
  cache.ResourceEventHandlerFuncs{
    AddFunc: func(obj any) {
      key, _ := cache.MetaNamespaceKeyFunc(obj)
      queue.Add(key) // 只入 key，不放完整对象
    },
    UpdateFunc: func(oldObj, newObj any) {
      oldPod := oldObj.(*corev1.Pod)
      newPod := newObj.(*corev1.Pod)
      if oldPod.ResourceVersion == newPod.ResourceVersion {
        return // 过滤纯 resync
      }
      key, _ := cache.MetaNamespaceKeyFunc(newObj)
      queue.Add(key)
    },
    DeleteFunc: func(obj any) {
      // obj 可能是 DeletedFinalStateUnknown tombstone
      key, _ := cache.DeletionHandlingMetaNamespaceKeyFunc(obj)
      queue.Add(key)
    },
  },
)

factory.Start(stopCh)
if !cache.WaitForCacheSync(
  stopCh, podInformer.Informer().HasSynced,
) {
  return fmt.Errorf("cache sync failed")
}

for processNextItem(queue, podInformer.Lister()) {
  // worker: Get key → Lister 读最新对象 → 幂等处理
}
Failure & consistency

重连、缓存一致性与 Resync

初始 List 与 Cache Sync

Informer 在初始 List 对象进入 Indexer 后才算 HasSynced。Controller 应先等待 WaitForCacheSync，再启动 worker，避免在空缓存上误删资源。

List snapshot → Replace Delta → Indexer → HasSynced=true

Watch 断开与 410 Gone

Watch 是长连接但不是永久连接。Reflector 自动重试；若 resourceVersion 已从服务端历史窗口淘汰，则重新 List 建立新基线。

watch closed → retry · RV expired → relist

Resync 不是重新 List

Resync 周期通常是把本地 Store 中的对象重新产生 Sync 通知，给控制器一次重新检查机会；它不等于定时访问 apiserver 全量 List。

local cache → synthetic Sync event → handler

缓存是最终一致

写请求直达 apiserver，而下一次 cache Get 可能短暂读到旧版本。逻辑应幂等，并通过 resourceVersion、Patch/重试处理冲突。

write API → watch propagation delay → cache catches up

Delete Tombstone

如果 Delete 事件到达时缓存里已没有对象，Handler 可能收到 DeletedFinalStateUnknown，必须用安全函数提取 key。

DeletionHandlingMetaNamespaceKeyFunc(obj)

SharedInformerFactory

同一资源类型共享 Reflector、DeltaFIFO 和 Indexer；多个 Controller/Handler 共享缓存，减少 apiserver 连接数和内存复制。

one List-Watch → one cache → many handlers
controller-runtime mapping

在 Kubebuilder 中这些组件藏在哪里

Manager

统一创建 Cache、Client、Controller、Webhook，并在选主成功后启动 Informer 与 worker。

Cache

底层为每种被 Watch 的 GVK 创建/复用 Informer。默认 client.Get/List 对缓存类型从这里读取。

For / Owns

For(&MyApp{}) Watch 主资源；Owns(&Deployment{}) Watch 子资源，并通过 OwnerReference 映射回 CR 的 Reconcile key。

APIReader

绕过 Cache 直接读取 apiserver，适合确实需要最新值的少数路径；不应成为默认读法，否则失去 Informer 的减压作用。

func (r *MyAppReconciler) SetupWithManager(mgr ctrl.Manager) error {
  return ctrl.NewControllerManagedBy(mgr).
    For(&appv1.MyApp{}).      // 主 CR Informer
    Owns(&appsv1.Deployment{}). // 子资源事件映射回 owner
    Complete(r)
}

func (r *MyAppReconciler) Reconcile(
  ctx context.Context, req ctrl.Request,
) (ctrl.Result, error) {
  var app appv1.MyApp
  // 默认走 Manager Cache；事件只给 key，这里读最新快照
  if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
    return ctrl.Result{}, client.IgnoreNotFound(err)
  }
  return r.reconcileDesiredState(ctx, &app)
}
误区 1：Informer 就是 Watch

Watch 只有增量流；Informer 还负责初始 List、恢复、缓存、索引和 fan-out。

误区 2：事件必须逐条处理

事件可能合并或重复。Controller 应读取最新状态做 level-triggered 收敛。

误区 3：DeltaFIFO 等于 WorkQueue

前者服务 Informer 缓存更新；后者服务业务 Reconcile 调度。

误区 4：Resync 会重新请求全量数据

典型 Resync 是本地缓存产生 Sync 通知，不是定时 Relist。

误区 5：Cache Get 是强一致读

它是 Watch 驱动的最终一致缓存，写后立即读可能短暂落后。

误区 6：Handler 中直接执行业务

Handler 应快速入队；耗时与重试逻辑放在 worker/Reconcile。

06 / Interview Essentials

CRD / Operator 与 K8s 高频面试题

先给 30 秒结论，再讲机制与边界。点击题目展开参考答案。

答题结构

是什么 → 请求怎么走 → 控制器怎么收敛 → 失败与边界。避免把 CRD 说成「另一种 Pod」或「直接跑在 etcd 里的脚本」。

Q01CRD 和 API Aggregation 有什么区别？怎么选型？

CRD 由 apiserver 内置 apiextensions 模块动态注册 REST，无需独立 APIServer 进程；Aggregation 通过 APIService 把请求转发到扩展 apiserver，适合复杂校验、大量逻辑或非 etcd 存储。

面试结论：大多数 Operator 用 CRD + controller-runtime；只有需要完全自定义 apiserver 时才考虑 Aggregation。

Q02GVK、GVR、Kind、Resource 分别是什么？

GVK 是 API 类型标识（manifest 里的 apiVersion/kind）；GVR 是 REST 路径中的 group/version/resource（复数 plural）。Kind 是类型名，Resource 是 URL 段，由 CRD spec.names 定义。

RESTMapper 负责 GVK ↔ GVR 映射；写 client 时要分清 typed client 与 dynamic client。

Q03CRD 的 structural schema 是什么？为什么重要？

v1 CRD 要求 schema 满足结构约束：例如 spec 下对象类型不能随意嵌套未知结构，避免 metadata 等字段被误放到错误位置，并支持 pruning 与 CEL。

非 structural 的旧 CRD 在新版本集群上受限；kubebuilder 默认生成 structural schema。

Q04spec 和 status 为什么要分开？status 子资源做什么？

spec 是用户期望；status 是系统观测。启用 subresources.status 后，更新 status 走独立 API，RBAC 可拆成 myapps 与 myapps/status，减少 spec/status 写冲突。

Reconcile 中改 spec 用 Update/Patch；回写 status 用 Status().Update 或 status subresource patch。

Q05Reconcile 为什么要设计成幂等、level-triggered？

同一对象会多次入队（重试、resync、子资源变化）。Reconcile 应基于当前 spec 对齐世界状态，而不是假设「只处理一次 CREATE 事件」。

Edge-triggered 易丢状态；level-triggered + workqueue 是 Kubernetes 控制器标准模式。

Q06Informer 和直接 List-Watch 有什么区别？

Informer = Reflector（List-Watch）+ DeltaFIFO + Indexer 本地缓存 + 事件分发。Reconcile 从 cache 读，降低 apiserver 压力，并让多个 Handler 共享同一份对象快照。

cache 是最终一致的；在 controller-runtime 中确需绕过缓存时使用 APIReader 直接读取 apiserver。

Q07WorkQueue 如何防止 Reconcile 风暴？

事件触发时只把 namespace/name 入队并 dedupe；同一 key 处理完前不会并行重复处理（单 worker 模型下）。失败则 rate limited requeue。

不要在一个 Informer handler 里做重逻辑；只做 enqueue。

Q08OwnerReference 和 Finalizer 分别解决什么问题？

OwnerReference 让 garbage collector 在删除 CR 时级联删除子资源（controller=true）。Finalizer 让 CR 在 DeletionTimestamp 后仍保留，直到控制器完成外部清理并移除 finalizer。

只有 OwnerReference 无法阻止「CR 删了但云资源还在」；外部依赖常用 finalizer。

Q09Mutating 和 Validating Webhook 的执行顺序？

先 Mutating（可改对象），再内置/OpenAPI 校验，再 Validating（只读校验）。任一失败可拒绝请求（取决于 failurePolicy）。

CRD default 在 schema 层；复杂 default 仍常用 mutating webhook。

Q10多版本 CRD 如何存储与 serving？Conversion 何时需要？

versions[] 中 exactly one storage: true；多个 served: true 可同时暴露。客户端读 v2 时 apiserver 可能通过 conversion webhook 转为 storage 版本再存 etcd。

单版本 CRD 不需要 conversion；升级 API 版本是常见面试深挖点。

Q11generation 与 observedGeneration 有什么用？

metadata.generation 在 spec 变化时递增（status 变化通常不增）。status 里 observedGeneration 表示控制器已处理的 spec 代数，用于判断「是否仍在上一次 spec 上运行」。

Conditions 应配合 observedGeneration，避免旧 status 误导用户。

Q12Operator 多副本如何避免重复 Reconcile？

使用 Leader Election（Lease 对象）；仅 leader 注册 controller。非 leader 进程可仍提供 webhook 或 metrics，取决于部署设计。

没有 leader election 的多副本会导致重复创建资源或冲突写。

Q13client-go 与 controller-runtime 的关系？

controller-runtime 基于 client-go，封装 Manager、Reconciler 接口、Webhook、Scheme 与 cache 共享。kubebuilder 项目默认用 controller-runtime。

底层仍是 ListWatch + workqueue；理解 client-go 有助于排查 cache 与 RBAC 问题。

Q14CR 的 RBAC 一般怎么设计？

人类用户：对 CR 的 get/list/watch/create/update/patch/delete；Operator ServiceAccount：对 CR 与 status 子资源、以及其创建的 Deployment 等资源的 verbs。ClusterRole + RoleBinding 或 namespace Role。

controller-gen 可生成 +kubebuilder:rbac 注解对应的 manifest。

Q15Server-Side Apply 和 CRD 开发有什么关系？

SSA 用 fieldManager 跟踪字段所有权，多控制器/用户协作同一对象时减少 patch 冲突。Operator 创建子资源时也常用 SSA 或 CreateOrUpdate。

面试可提：CR 本身 apply 与 Controller patch 子资源是不同层级的协作问题。

Q16CEL 校验能否替代 Validating Webhook？

CEL 适合声明式、无外部依赖的规则（范围、跨字段）。需要查集群其他对象、调用外部系统、复杂业务仍用 webhook。

CEL 在 apiserver 内执行，延迟低；webhook 要注意 timeout 与高可用。

Q17CRD Established=False 常见原因？

schema 不合法、版本名冲突、conversion 配置错误、与已有 CRD 名称冲突等。需 kubectl describe crd 看 conditions message。

未 Established 时不要假设 REST 已完整可用。

Q18如何调试 Reconcile 不生效？

检查：CRD/CR RBAC、Informer 是否 Watch 正确 GVK、WorkQueue 是否 requeue 错误、子资源 Create 是否 AlreadyExists、status 子资源权限、webhook 是否拒绝。

启用 controller 日志、kubectl describe events、metrics（reconcile_errors_total）。

K01kube-apiserver 为什么是 Kubernetes 的核心？

它统一提供 REST、鉴权、RBAC、准入、审计、版本转换和 Watch，也是核心组件访问 etcd 的唯一入口。其他组件主要通过 API 对象解耦。

Kubernetes 的中心是声明式 API，不是组件间互相远程调用。

K02Scheduler 和 kubelet 分别负责什么？

Scheduler 为未绑定 Pod 选择 Node 并写入 binding；kubelet Watch 本节点 Pod，通过 CRI/CNI/CSI 把 PodSpec 落地并汇报状态。

Scheduler 不启动容器，kubelet 不负责全局节点选择。

K03Deployment 创建 Pod 的完整控制链是什么？

Deployment Controller 创建 ReplicaSet，ReplicaSet Controller 创建 Pod；Scheduler 绑定 Node；目标 Node 上 kubelet 调用运行时创建容器。

Deployment → ReplicaSet → Pod → Scheduler → kubelet → CRI。

K04CRI、CNI、CSI 分别解决什么问题？

CRI 是 kubelet 与容器运行时接口；CNI 负责 Pod 网络；CSI 负责存储供应、Attach 与 Mount。它们是三个独立插件边界。

不要把 kube-proxy 说成 CNI：前者主要实现 Service 转发，后者实现 Pod 网络。

K05kube-proxy 与 CoreDNS 的职责区别？

CoreDNS 负责把 Service 名解析为 ClusterIP 或 Endpoint；kube-proxy/替代 eBPF 数据面负责把 Service VIP 流量转发到后端 Pod。

DNS 解决“名字对应哪个地址”，数据面解决“数据包如何到达后端”。

K06Operator 属于 Kubernetes 控制面吗？

通常不属于内置控制面。Operator 是以 Deployment/Pod 运行的自定义控制器，但遵循与内置 controller-manager 相同的 List-Watch + WorkQueue + Reconcile 模式。

它扩展 Kubernetes API 行为，不意味着必须部署在 control-plane Node。

K07组件之间为什么大量使用 List-Watch 而不是直接 RPC？

组件围绕 apiserver 中的持久化期望状态异步协作，可独立重启、重试和水平扩展；List 提供初始快照，Watch 提供增量变化。

Informer 是建立在 List-Watch 之上的缓存、索引和事件分发封装。

K08etcd 故障时已运行 Pod 会立即停止吗？

通常不会。节点上的现有容器继续运行，但 API 写入、调度、控制器收敛与状态更新受阻；控制面恢复后再继续同步。

etcd 存储控制面状态，不在业务数据包和容器进程的运行主路径上。
